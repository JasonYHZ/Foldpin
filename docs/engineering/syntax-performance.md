# 高亮长度上限评估

2026-09-08。用户询问是否超过一万字符就关闭高亮，并希望负担允许时尽量多渲染。

**决定：不降低为 10,000，保留现有 24,000 UTF-16 单元保护上限。暂不直接提高到 50,000 或取消限制。** 达到上限只关闭代码着色，完整文字、等宽显示、块背景、编辑、复制和保存仍然保留。

## 测量方法

在当前 arm64 Mac、macOS 26.6.2 上，以 SwiftPM Release 构建运行离屏基准，没有创建可见窗口、操作用户笔记或剪贴板。四组人工代码片段为 Java、含 script 的 HTML、单行 JavaScript、单行 JSON 对象片段；用重复片段组成目标长度，各测两次。这是语法与文本显示测量，样本不是完整可执行程序。

基准调用项目真实的 CodeSyntaxEngine、BlockTextCodec.render 和 PaperTextView，不以 Node.js 的解析性能代替系统 JavaScriptCore。为了测量超出现有限制的完整高亮，脚本只在临时源码副本中将字符限制升到 300,000、缓存预算升到 64 MiB；生产源码仍为 24,000 和 2 MiB。每个样本都检查解析结果和缓存词元存在，防止误把无高亮回退当成性能提升。

分开记录后台解析、主线程生成带样式文字、安装到原生编辑器、首次代码块几何计算和再次几何计算。安装时间包含内部带样式文字生成，不能与 render 时间相加。几何指标对应现有 codeBlockSurfaces 路径，不是屏幕完整帧时或触控板滚动体验。

## 对产品的含义

原生避免了逐纸片 WebView 的开销，但不会消除词元上色、NSTextStorage 更新与 TextKit 排版成本。即使解析在后台，颜色应用仍发生在主线程。同样字符数，HTML / JSON 这类词元较密的片段需要更多属性操作，不能只凭字符数推断负担很轻。

一万字符没有必要成为新的硬边界，现有 2.4 万已经允许更多内容正常高亮。但 5 万样本仅生成带样式文字就可能花约 85 ms，原生安装与几何开销还更高；直接放宽会增加可感知停顿的风险。保留 2.4 万是当前实现下的折中，并非已证明所有低配设备或多纸片场景都流畅的性能承诺。

后续需要更多长代码支持时，优先减少主线程属性操作、只刷新可见或变更区间，再评估上限；不应只改一个数字。关闭高亮也不会消除极长正文自身的排版开销。本轮没有测量多纸片内存、真实滚动帧率或不同硬件，未新增设置项或截断用户内容。

## 复现

从产品目录运行：

```sh
python3 scripts/benchmark-syntax.py /private/tmp/foldpin-syntax-benchmark.json
```

脚本与 fixture 位于 scripts 下，不加入常规单元测试、不随应用打包。输出只包含人工样本与耗时，构建及临时源码在 /private/tmp。普通功能改动不需要反复跑此基准。
